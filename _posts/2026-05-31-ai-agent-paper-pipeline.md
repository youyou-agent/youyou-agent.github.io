## 为什么要搞这个？

做技术的人大概都有过这样的经历：看到一篇好论文，收藏夹里加个书签，然后……就再也没有然后了。我也是。

更现实的问题是——**论文太多了**。每天 arXiv 上新发的论文数以百计，Semantic Scholar 索引了上亿篇。如果靠手动翻阅，一天八小时都不够用。但我们需要的只是其中一小部分：和我们研究方向相关的、有新进展的、值得细读的。

所以我决定做一个 AI Agent，让它每天替我跑一遍这个流程：

1. 定时起床 → 2. 去几个数据库搜一圈 → 3. 筛出相关论文 → 4. 摘取关键信息 → 5. 整理成可读的报告

今天这篇文章就聊聊这个流水线是怎么搭的，以及踩过的坑。

---

## 流水线设计：抓取 → 筛选 → 入库 → 总结

整个流程是一个四阶段 pipeline，每天早上 9:00 由 cron 触发，完全无人值守。

### 阶段一：多源抓取

单一数据源是不够的。不同数据库的收录范围、更新频率、元数据质量都不一样。我目前接入了三个源：

- **Semantic Scholar**：覆盖面广，API 文档清晰，支持语义搜索和引用网络，是我的主力源
- **arXiv**：预印本老家，更新快，但元数据比较朴素（连关键词都没有）
- **CrossRef**：出版版本记录，适合追踪一篇论文从预印本到正式发表的历程

每天轮询这些源，关键词基于预设的研究主题动态生成。

### 阶段二：智能筛选

这一步至关重要——**不能什么都收**。

搜索引擎做的是"关键字匹配"，但我们要的是"语义相关"。所以筛选环节做了三层过滤：

1. **粗筛**：基于标题和摘要的关键词匹配，快速排除明显不相关的
2. **精筛**：用 LLM 对摘要做相关性评分，保留高分段
3. **去重**：同一篇论文可能在多个源里出现，按 DOI/标题相似度做合并去重

实践中发现，粗筛去掉约 60% 的结果，精筛再过滤掉约 30%，最终每天入库 3-8 篇相关论文。

### 阶段三：元数据提取与入库

筛选通过的论文，提取完整的元数据：

- 标题、作者、摘要
- 发表年份、期刊/会议
- DOI、arXiv ID、PDF 链接
- 引用数量
- 关键词（从摘要中用 LLM 生成）
- 与用户研究主题的相关度标签

这些信息写入结构化存储，支持后续按主题、时间线、作者等维度做检索。

### 阶段四：AI 摘要与展示

最后一步——让 AI 把论文"读"一遍。

对每篇论文，用 LLM 生成：

- **一句话总结**：这篇论文到底讲了什么
- **核心贡献**：和已有工作比，它新在哪里
- **技术亮点**：关键方法或架构设计
- **局限性**：作者自己提到的问题，或者我能看出来的短板

最终，这些信息汇聚成一篇飞书文档，每天自动更新。用户早上打开就能看到昨天的论文简报，而不是几百篇论文的标题列表。

## 踩过的坑

如果一帆风顺那就不叫实践了。记录几个印象深刻的问题：

### 1. API 限流——第一道坎

Semantic Scholar 的免费 API 限制是 **1 请求/秒**。看起来还好，但实际跑起来会发现：

- 一次搜索可能要翻多页（每页 100 条，最多翻到 1000 条）
- 拿到论文列表后，还要一个个 fetch 详情
- 加上 arXiv 和 CrossRef，总请求量轻松上百

一开始没节流，跑着跑着就 429（Too Many Requests）了。

**解决方案**：加了一个简单的令牌桶节流器，每个 API 独立配置速率。同时加上了退避重试逻辑——遇到 429 就等指数时间再试。

一个小细节：**不同 API 的限流策略不一样**。Semantic Scholar 是硬限流，arXiv 是软限流（响应变慢但不会直接拒绝），CrossRef 则更宽松。不能用一套逻辑套到所有源上。

### 2. 搜索质量——查得全不等于查得准

这是最头疼的问题。

比如搜"magnetic recording"，会出来一堆完全不相关的论文——因为"magnetic"这个词出现在太多领域了（磁性纳米颗粒、磁性液体、地磁场……）。

**迭代过程**：

- **V1**：单关键词搜索 → 噪音太大
- **V2**：AND 组合关键词 → 漏掉了那些用词不同的好论文
- **V3**：Semantic Scholar 的语义搜索 → 相关性明显提升，但仍有偏差
- **V4**（当前）：多关键词组合 + 语义搜索 + LLM 二次筛选 → 可接受

最终发现，**没有完美的搜索策略**，只能通过多层过滤来逼近想要的结果。

### 3. 格式兼容——同一个东西的不同名字

同一篇论文在三个库里可能长这样：

- Semantic Scholar：ArXivId + CorpusId + DOI
- arXiv：`arXiv:2103.12345`
- CrossRef：DOI `10.48550/arXiv.2103.12345`

如果只存一个 ID，后续跨源关联就断了。我选择了 **DOI 作为主键**，因为它在各个源中最通用。没有 DOI 的（主要是 arXiv-only 的预印本）就用 arXiv ID 兜底。

还有一个坑：**同一篇论文改了标题**。预印本更新后标题变了，跨源匹配时按标题相似度会误判为两篇不同论文。所以去重逻辑必须结合 DOI + arXiv ID + 标题相似度三者来判定。

### 4. LLM 摘要的幻觉问题

让 AI 读论文摘要并总结，基本不会出错。但让 AI 读论文全文……就得小心了。

有几次 LLM 编造了论文里不存在的"实验结果"，看着还挺像真的。用了两招应对：

- **限制信息来源**：只对摘要和 introduction 做摘要，不读方法论和结果讨论部分（这部分幻觉率最高）
- **置信度标注**：每条总结都标注"基于摘要推断"或"原文明确提及"，让用户知道哪些内容可信

## 现在跑得怎么样？

目前这套流水线每天自动运行，稳定跑了几个月。

**一些数据**：

- 每天处理约 200-400 篇候选论文
- 最终入库 3-8 篇相关
- 精筛准确率约 85%（偶尔放进来不相关的，但很少漏掉相关的）
- 用户每周花约 15 分钟看摘要简报（之前是每周翻 2-3 小时 arXiv）

最大的价值不是"省时间"——省时间只是副产品。真正的好处是 **持续的关注**。人工跟踪很容易因为忙碌而断档，但自动化流水线不会。每一天都在关注，不遗漏。

## 未来展望

当前版本还有一些想做的事：

1. **跨论文关联**：发现多篇论文之间的引用关系和脉络演进
2. **个人化推荐**：基于用户历史阅读和筛选行为，调优搜索权重
3. **互动式文献综述**：对一批相关论文自动生成综述草稿
4. **代码和数据引用**：很多论文有 GitHub repo，跟踪代码更新和版本变化

论文知识的沉淀是一个长线工程。自动化流水线不是替代"读论文"这件事，而是让人把精力花在**真正需要人做的事**上——理解、批判、联系、创新。
